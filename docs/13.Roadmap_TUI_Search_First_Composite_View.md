# Roadmap: TUI Search-First Composite View

## Overview

**Epic:** Search-First Composite View

### Goal

Give the TUI a single natural-language entry point that returns a
composed, multi-block answer for a query — price, key stats, screening
score, SMC signal, and narrative summary in one screen — similar in
spirit to Google Finance's beta search experience. Builds on top of the
already-implemented Phase 1–4 TUI foundation; does not replace it.

------------------------------------------------------------------------

## Relationship to Existing Roadmap

This roadmap extends `12.Roadmap_Terminal_User_Interface.md` (Phases
1–4, already implemented and merged/in review). It does not revise
those phases. Phase 1–4's dashboard, workspaces, and CLI parity remain
fully intact — this roadmap adds a new landing experience on top.

------------------------------------------------------------------------

## Prerequisite

-   `natural()` intent engine must support dispatching to multiple
    underlying functions for one query, not routing to a single clause
    as it does today.
-   Existing render components (`ResultTableScreen`,
    `ReportViewerScreen`) must become embeddable blocks/widgets, usable
    inside a composite screen, not only as standalone destinations.
-   Underlying data/service layer (`IDXProvider.fetch_financials`,
    yfinance + `curl_cffi` fix, SMC screening engine, scoring system)
    is reused unchanged. This roadmap does not touch that layer.

------------------------------------------------------------------------

# Phase 5 --- Composite Query Engine

## Objective

Let one query trigger multiple existing service functions at once and
return a single aggregated result, instead of routing to exactly one
feature.

### Scope

-   Detect when a query targets a single entity (e.g. a ticker) that
    warrants multiple data blocks, versus a query that only needs one
    (e.g. "top gainers").
-   Parallel dispatch layer: call relevant existing functions
    concurrently (quote, financials, screening score, SMC signal) for
    that entity.
-   Aggregation contract: one structured result object combining
    outputs from multiple functions, each tagged by block type
    (`quote`, `stats`, `signal`, `narrative`, ...).
-   Partial-failure handling: if one underlying call fails or returns
    no data, the aggregate still returns with that block marked
    unavailable — it does not fail the whole query.

### Expected Outcome

A query like "BBCA" or "analisa BBCA" triggers several existing
functions at once and returns one combined result, ready to render.

------------------------------------------------------------------------

# Phase 6 --- Composite Render Screen

## Objective

Render an aggregated result as multiple blocks in one screen, instead
of routing to a single view type.

### Scope

-   New composite screen that renders N blocks (quote header, stats
    table, SMC signal panel, narrative panel) from Phase 5's aggregate
    result.
-   Reuse `ResultTableScreen` / `ReportViewerScreen` internals as
    embeddable sub-components rather than full standalone screens.
-   Per-block graceful degradation: a missing/failed block shows a
    clear "data unavailable" state; other blocks render normally.
-   Visual separation between AI-written narrative text and
    structured/fetched data, so it's always clear what's computed
    versus summarized.

### Expected Outcome

A single query returns a Google-Finance-style composite panel, without
the user needing to open separate features one at a time.

------------------------------------------------------------------------

# Phase 7 --- Search-First Landing

## Objective

Make the search box the default screen on launch; the Phase 1–4
dashboard becomes a secondary, still fully available path.

### Scope

-   Landing screen on `screening tui` becomes the search input, not
    the dashboard.
-   Keyboard shortcut to reach the classic dashboard/menu for direct
    feature access (power users, or queries that don't fit the
    composite model).
-   No functional change to Phase 1–4 screens — only their position in
    the navigation flow changes.

### Expected Outcome

The TUI opens straight into a search experience. Menu-driven navigation
from Phase 1–4 remains available, but optional.

------------------------------------------------------------------------

# Recommended Implementation Order

1.  Composite Query Engine (Phase 5) — backend/orchestration only, no
    UI change yet; testable in isolation through the CLI before any
    screen work starts.
2.  Composite Render Screen (Phase 6) — depends on Phase 5's aggregate
    result contract.
3.  Search-First Landing (Phase 7) — routing/cosmetic change, lowest
    risk, done last once the composite view is proven to work.

------------------------------------------------------------------------

# Success Criteria

-   A single free-text query for one ticker returns price, key stats,
    and screening signal together, without manually navigating between
    separate features.
-   A failure in one data source does not block the rest of the
    composite view from rendering.
-   Phase 1–4 dashboard and existing CLI remain fully functional and
    unchanged.
-   AI-generated narrative is visually and structurally distinguished
    from fetched/computed data — no ambiguity about which is which.

------------------------------------------------------------------------

# Design Principles

-   The underlying service/data layer is reused as-is. No
    reimplementation, and no direct AI-to-raw-API calls (yfinance/IDX
    endpoints stay behind the existing fixed, tested service functions).
-   AI orchestrates which functions to call and narrates the result. It
    does not compute or fabricate financial figures itself.
-   CLI/service functions remain the single source of truth; the
    composite engine calls them, it never bypasses them.
-   Composite rendering degrades per-block, never fails the whole
    screen for one missing data point.

------------------------------------------------------------------------

# Out of Scope

This roadmap does not introduce new data providers, new financial
calculations, or changes to the SMC screening engine itself. It does
not remove or replace the Phase 1–4 dashboard, which remains available
as a secondary navigation path.

------------------------------------------------------------------------

# Open Questions

Decisions needed before implementation starts:

-   **Layout:** blocks stacked vertically with scroll, or tabbed with
    switch-between-blocks navigation?
-   **Query scope:** does the composite view apply only to single-entity
    lookups (one ticker), or also to aggregate queries ("top gainers
    sektor bank")? Current assumption: aggregate queries stay
    single-block (table); composite applies mainly to single-entity
    lookups.
-   **Concurrency limit:** how many underlying calls can safely run in
    parallel per query, given the rate-limit handling already in place
    for IDX/yfinance?

------------------------------------------------------------------------

# Alignment with Product Vision

This roadmap moves the TUI toward the original product vision — a
single natural-language entry point with AI-composed structured output
(from `BSJP_AI_Blueprint.md`) — without requiring the backend/frontend
stack originally planned for `buat-web-screening`. It reuses the
platform's existing AI, screening, and research capabilities; it does
not introduce a parallel implementation of any of them.
